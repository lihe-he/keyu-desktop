# 课屿 · Keyu Desktop

**课程一处，学习有序。**

课屿是一款面向大学生的网课聚合与学习辅助桌面应用，旨在将分散在不同平台的课程、学习计划和资料入口集中到一个清晰、易用的工作空间中，减少重复操作，让学习安排更加有序。

用户在自己的电脑上登录自己的网课账号，通过统一界面管理课程、控制播放、切换章节并接收学习提醒。课屿以本地优先为设计原则，核心任务在用户设备上执行，不依赖集中托管网课账号的云端服务。

> **项目状态：规划阶段。** 本文描述产品目标与拟采用的技术方案，不代表相关功能已经实现。当前尚未确认任何网课平台的兼容性，也未提供经过验证的安装包或启动命令。

## 项目简介

**课屿**的名字来自“课程”与“岛屿”：把分散的课程、资料和学习安排，汇聚成属于自己的学习小岛。

项目希望提供的不是一个简单的网址收藏夹，也不是把多个网页机械地堆叠在一起，而是一个围绕真实学习流程组织的桌面工具：

- 用统一入口访问不同网课平台。
- 用一致的方式查看课程和章节。
- 在平台允许的范围内减少播放与章节导航中的重复操作。
- 用学习计划和提醒帮助用户安排节奏。
- 用可恢复的任务记录减少中断带来的困扰。
- 逐步连接课程、资料与阅读场景。

**项目名称：** 课屿  
**英文名称：** Keyu Desktop  
**仓库名称：** `keyu-desktop`  
**产品形态：** 本地优先桌面应用

## 为什么做课屿

大学生的在线学习通常分布在多个平台中：课程入口不同、登录状态分散、章节操作重复，资料和学习记录也不容易统一整理。

课屿希望减少这些操作上的负担，让用户更容易回答几个简单的问题：

- 我有哪些课程需要继续学习？
- 上次学到哪一章了？
- 今天计划学习什么？
- 当前任务正常运行，还是需要我处理？
- 与这门课相关的资料放在哪里？

项目的目标是**帮助大学生组织学习、减少重复操作和管理压力**，而不是把学习本身简化为一个完成百分比。

## 核心功能规划

以下功能均为规划内容，实际支持情况将随开发和测试结果更新。

### 1. 多平台课程聚合

- 集中展示已接入的网课平台。
- 通过平台原有页面登录账号。
- 读取适配平台中用户可访问的课程和章节。
- 在统一界面中浏览、筛选和选择课程。
- 展示各平台适配器的能力和兼容状态，明确区分“支持”“不支持”和“待验证”。

### 2. 播放控制与章节导航

- 控制已适配课程的播放与暂停。
- 读取当前章节的真实播放状态。
- 在视频结束且平台允许进入下一章节时进行切换。
- 为受浏览器策略限制的自动播放保留必要的用户操作入口。
- 分开展示本地观察到的播放进度与平台认定的完成状态。

### 3. 学习任务管理

- 将课程加入本地任务队列。
- 支持开始、暂停、停止和恢复。
- 第一版默认一次执行一个课程任务，其他任务排队。
- 持久化关键任务状态，便于中断后继续。
- 在恢复前重新检查登录状态、当前章节和播放器状态，不盲目沿用旧记录。

### 4. 学习计划与提醒

- 设置学习时间和提醒计划。
- 提供学习提醒、休息提醒和任务完成提醒。
- 当任务需要用户介入时，通过界面和系统通知提示。
- 支持关闭主窗口后按用户设置驻留托盘。
- 电脑休眠唤醒后重新检查任务和到期提醒。

### 5. 异常提示与执行记录

- 展示任务执行过程中的关键事件。
- 区分登录过期、网络异常、播放失败和平台适配失效等情况。
- 对无法确认的页面状态暂停处理，避免错误切换章节。
- 提供有助于排查问题的本地日志，并对敏感信息进行脱敏。

### 6. 资料收藏与阅读

作为后续扩展方向，计划逐步加入：

- 课程相关资料和链接收藏。
- 本地收藏的分类与搜索。
- 课程与资料之间的关联。
- 适合桌面场景的阅读入口。

资料功能优先围绕本地收藏和用户可访问的内容展开，不与播放任务调度耦合，也不承诺对所有网站进行全文检索。

## 预期使用流程

1. 打开课屿，选择一个已适配的平台。
2. 在平台原有登录页面中登录自己的账号。
3. 查看课程和章节，选择需要学习的内容。
4. 开始播放，或将课程加入学习任务队列。
5. 应用读取实际播放状态，在满足条件时切换章节。
6. 遇到登录失效、验证码、章节锁定等情况时，暂停并提示用户处理。
7. 用户可以随时暂停任务、调整计划或退出应用。
8. 下次启动时读取本地记录，重新核对平台状态后继续。

## 设计原则

### 本地优先

核心业务逻辑、任务记录和应用设置在本机运行与保存。第一版不要求用户注册课屿账号，也不需要部署自己的后端服务。

本地优先不等于完全离线：访问网课平台、登录账号和播放在线课程仍然需要网络。

### 状态真实、结果可解释

本地视频播放结束，不代表网课平台已经认定完成。两类状态独立记录；无法读取平台完成结果时，明确展示为未知或待确认。

### 用户可以随时接管

任务提供清晰的开始、暂停与停止入口。遇到需要人工处理的情况时暂停，不通过无限重试掩盖异常。

### 平台差异集中管理

每个网站通过独立适配器接入，页面选择器、接口字段与状态解析逻辑集中在适配器内，避免散落在界面组件和调度代码中。

### 先稳定，再扩展

先验证一个平台的完整学习流程与异常恢复，再扩大接入数量；优先保证任务状态可靠，而不是追求同时打开更多页面。

## 技术栈与架构

拟采用 **Electron + Vue 3 + TypeScript + SQLite** 的模块化本地架构。

| 层级         | 技术栈                                 | 主要职责                                                     |
| ------------ | -------------------------------------- | ------------------------------------------------------------ |
| 桌面应用层   | Electron                               | 窗口管理、应用生命周期、内嵌浏览器、系统托盘与通知。         |
| 界面展示层   | Vue 3 + TypeScript + Vite              | 平台入口、课程列表、任务页面、学习计划、资料和设置界面。     |
| 界面状态层   | Pinia                                  | 管理界面状态，接收执行层更新，不独立维护另一套任务调度逻辑。 |
| 进程通信层   | Electron IPC + preload + contextBridge | 在自有界面与本地功能之间提供受限、可校验的通信接口。         |
| 网站适配层   | TypeScript + 独立平台适配器            | 登录检测、课程解析、播放控制、章节导航及平台状态读取。       |
| 任务执行层   | Electron 主进程中的 TypeScript 模块    | 任务队列、状态转换、异常处理、暂停恢复与提醒调度。           |
| 账号与会话层 | Electron Session 独立持久化分区        | 按平台与账号隔离 Cookie 和登录状态。                         |
| 本地数据层   | SQLite + better-sqlite3                | 保存课程缓存、任务记录、计划、收藏、设置和必要的事件记录。   |
| 提醒与通知层 | 本地计划调度 + Electron Notification   | 学习与休息提醒、任务完成提醒、人工处理提示。                 |
| 测试层       | Vitest + Playwright                    | 单元测试、适配器解析测试，以及关键桌面交互流程的自动化验证。 |
| 打包交付层   | electron-builder                       | 构建安装包、打包原生依赖，并根据发布需求配置签名与更新。     |

这些层级是**同一个桌面应用内的职责划分**，不是多个需要单独部署的服务。

### 进程职责

- **自有界面进程**：展示课程和任务状态，接收用户操作，通过受限接口发送指令。
- **主进程**：管理窗口、会话、任务调度、数据库和系统能力。
- **第三方网站页面**：在隔离环境中运行，由适配逻辑执行必要的网页操作，不获得应用的文件和数据库权限。

任务状态以执行层为准，界面状态只是其展示结果。切换应用内部页面不应意外中止任务，但承载播放的网站页面仍需保持可用。

### 为什么第一版不加入 Java 服务

Java 能胜任本地业务处理，但当前核心需求主要集中在网页交互和桌面能力上。额外加入 Java 会增加运行时打包、进程管理和本地通信成本。

在没有现成 Java 业务代码需要复用的情况下，先用一套 TypeScript 完成核心功能更直接。未来若需要应用账号、跨设备同步或自有资料服务，再考虑引入 Spring Boot 与 PostgreSQL 服务端。

## 平台适配机制

各平台并不一定具备相同能力，因此适配器需要明确描述自身支持范围，而不是强行提供一套看似完整的功能。

| 能力         | 说明                                                 |
| ------------ | ---------------------------------------------------- |
| 登录检测     | 判断当前账号是否处于可用登录状态。                   |
| 课程发现     | 获取用户可访问的课程和基本信息。                     |
| 章节读取     | 获取目录、当前章节及可进入状态。                     |
| 播放控制     | 对已适配播放器执行播放、暂停等必要操作。             |
| 状态读取     | 读取实际播放进度、结束状态和错误信息。               |
| 章节切换     | 在平台允许且满足条件时进入下一章节。                 |
| 完成状态读取 | 读取平台实际展示的完成结果；不可获取时保留未知状态。 |

接入时优先使用平台提供的官方接口；需要网页交互时，适配逻辑应保持最小职责，并将网站返回内容按不可信输入处理。

网站改版、播放器更新、登录流程变化或嵌入限制，都可能影响兼容性。平台支持列表应记录验证结果，而不是仅根据“可以打开网页”判断已经支持。

## 数据与隐私设计

以下是实现时需要遵守的设计约束，不代表已完成安全验证。

- 登录通过网课平台自身页面完成，不建立集中收集平台密码的服务。
- 不同平台和账号使用独立的持久化会话分区。
- 不向 SQLite 额外复制保存网站密码、完整 Cookie 或访问令牌。
- 确有必要保存的敏感配置使用系统支持的安全存储能力，并检查目标系统上的实际可用性。
- 日志不记录明文密码、Cookie 或访问令牌。
- 第三方网页关闭 Node 集成，启用上下文隔离与沙箱。
- 自有界面的高权限 IPC 接口不向第三方页面开放，并校验调用来源和参数。
- 限制页面导航、新窗口和外部链接的处理方式。
- 提供针对单个账号的退出和会话清理入口，避免影响其他账号。
- 本地数据库与浏览器会话仍需依靠操作系统账号和文件权限保护，不能仅因“存储在本地”就视为已加密。

“登录态留在本机”不意味着没有网络传输：用户登录和学习时，网课平台仍会按其自身流程接收请求；课屿的设计目标是不把这些登录凭据额外集中上传到项目自有服务器。

## 支持范围与运行边界

### 操作系统

计划优先在 **Windows** 上开发与验证。Electron 提供跨平台基础，但 macOS 和 Linux 上的打包、通知、凭据保护及播放器兼容性仍需分别测试，不提前承诺支持。

### 网课平台

目前尚未确认任何平台的兼容性。首期将选择一个目标平台验证完整流程，再逐步扩展。

### 任务执行

- 第一版默认单任务执行，避免多页面同时播放和争抢资源。
- 登录过期、验证码、章节锁定或页面状态无法确认时暂停处理。
- 不依赖固定等待时长推定课程完成。
- 后台播放和自动播放可能受平台、浏览器策略、系统休眠与媒体保护机制限制。
- 关闭窗口后是否驻留托盘，应由用户设置决定；应用彻底退出后，不再执行本地任务。

### 学习提醒

应用内的提醒调度依赖应用进程运行。系统通知权限或勿扰设置可能影响提示展示，因此提醒记录也应保留在应用界面中。

### 功能边界

首期聚焦课程聚合、播放控制、章节导航和学习提醒，不纳入自动答题、作业提交、伪造学习进度或绕过平台访问限制等能力。

## 常见问题

### 课屿是一个需要部署服务器的网站吗？

不是。它规划为安装在用户电脑上的桌面客户端，核心功能在本地运行，第一版不要求用户部署后端服务。

### 使用前需要安装 Java 吗？

不需要。当前拟采用 Electron 与 TypeScript 技术路线，不包含 Java 本地运行时。

### 可以接入所有网课网站吗？

不能提前保证。每个平台的登录、播放器和章节机制不同，需要独立适配与验证。当前没有已确认兼容的平台。

### 播放结束就代表课程完成了吗？

不一定。平台可能有独立的完成判定逻辑，应用应分别展示播放状态和平台完成状态，无法读取时明确标记为未知。

### 关闭窗口后还能继续吗？

计划提供驻留托盘选项，但承载播放的网站页面仍需保持运行，且后台播放是否可用必须逐平台验证。彻底退出应用后，本地任务和提醒不会继续执行。

### 可以离线学习吗？

本地记录、设置和部分收藏可以设计为离线可用，但在线课程的访问和播放通常需要网络，不承诺下载受保护课程或离线播放。

### 会增加云端同步吗？

可以作为后续方向评估，但不属于首期范围。若引入云端，优先同步用户选择的收藏、计划等应用数据，而不是集中托管网课平台登录凭据。
